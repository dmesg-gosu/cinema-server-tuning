## TCP Network Stack

### net.core.rmem_max и net.core.wmem_max

**Что это:** Максимальный размер буфера для приёма (rmem) и передачи (wmem) TCP данных.

**Значение:** `134217728` (128 MB)

**По умолчанию:** `4194304` (4 MB)

**Почему изменяем:**
- Большие файлы (кино 50GB+) требуют больших буферов
- Без достаточного буфера — потери пакетов и замедление скачивания
- Каждый TCP поток может использовать до этого размера

**Расчёт:**
```
Оптимальный размер = (BDP) Bandwidth-Delay Product
BDP = (пропускная способность в Mbps / 8) * RTT в сек

Пример:
- Сеть: 1 Gbps
- RTT: 10ms
- BDP = (1000 / 8) * 0.01 = 1.25 MB
- Берём с запасом: 128 MB (для всплесков и резервирования)
```

**Команда проверки:**
```bash
sysctl net.core.rmem_max net.core.wmem_max
```

### net.ipv4.tcp_rmem и net.ipv4.tcp_wmem

**Что это:** Трёхзначные значения: `min default max` для автоматической адаптации буфера TCP.

**Значение:** 
```
net.ipv4.tcp_rmem = 4096 87380 67108864
net.ipv4.tcp_wmem = 4096 65536 67108864
```

**Что означает:**
- `4096` — минимум (4 KB)
- `87380` — начальное значение по умолчанию (~85 KB)
- `67108864` — максимум (64 MB)

**Почему эти значения:**
- Минимум 4KB — стандарт для всех сокетов
- Начальное 85KB — хороший компромисс для среднего трафика
- Максимум 64MB — достаточно для большинства случаев (может быть 128MB для очень высоких скоростей)

**Как работает:**
```
Ядро автоматически масштабирует буфер:
- Начинает с 85KB
- При достаточном трафике — растёт до 64MB
- Если трафик уменьшится — сжимается обратно
```

**Команда проверки:**
```bash
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem
cat /proc/net/tcp  # Смотри столбец tx_queue
```

### net.ipv4.tcp_congestion_control

**Что это:** Алгоритм контроля перегрузки TCP (как реагировать на потери пакетов).

**Значение:** `bbr`

**По умолчанию:** `cubic` (на большинстве Ubuntu)

**Варианты:**
- **cubic** — старый, проверенный, медленнее адаптируется к потерям
- **bbr** — новый (Google), быстро реагирует на перегрузку, лучше для высоконагруженных сетей
- **reno** — очень старый, не используем

**Почему BBR:**
- Лучше работает с потерями пакетов (нестабильные каналы)
- Не требует зависимости от потерь — использует задержку
- Быстрее заполняет пропускную способность
- Хорош для спутниковых и наземных сетей

**Проверка:**
```bash
sysctl net.ipv4.tcp_congestion_control
cat /proc/sys/net/ipv4/tcp_available_congestion_control  # Доступные алгоритмы
```

**Требует:** Linux 4.9+ (есть во всех современных системах)

### net.ipv4.tcp_window_scaling

**Что это:** Масштабирование TCP окна (Wscale) для больших пропускных способностей.

**Значение:** `1` (включено)

**По умолчанию:** `1` (обычно включено по умолчанию)

**Почему нужно:**
- Без масштабирования — максимальное окно 65KB
- С масштабированием — может быть до 1GB
- Необходимо для гигабитных сетей

**Формула:**
```
Макс TCP окно = 65535 * 2^(Wscale)
Wscale может быть 0-14

Пример:
Wscale=7 → 65535 * 2^7 = 8.4MB
Wscale=14 → 65535 * 2^14 = 1GB
```

---

### net.ipv4.tcp_timestamps

**Что это:** Включение TCP timestamps для более точного измерения задержек.

**Значение:** `1` (включено)

**Почему нужно:**
- Более точный RTT (Round Trip Time)
- Помогает при потерях пакетов
- Защита от "устаревших пакетов" (PAWS)
- Включение не вредит производительности

---

### net.ipv4.tcp_fastopen

**Что это:** Ускорение подключения (TFO — TCP Fast Open).

**Значение:** `3` (1=client, 2=server, 3=both)

**Экономия:**
- Обычное соединение: 3-way handshake (3 пакета)
- С TFO: данные передаются в первом пакете
- Экономия одного RTT при каждом новом соединении

---

### net.ipv4.tcp_tw_reuse

**Что это:** Переиспользование TIME_WAIT сокетов для новых соединений.

**Значение:** `1` (включено)

**Почему нужно:**
- По умолчанию TIME_WAIT сокет ждёт 60 сек перед удалением
- При большом количестве соединений — портов может не быть
- С tw_reuse — можно переиспользовать порты
- Безопасно если включено net.ipv4.tcp_timestamps

---

### net.core.somaxconn и net.ipv4.tcp_max_syn_backlog

**Что это:** Размер очереди входящих соединений.

**Значение:** `65535` (оба параметра)

**По умолчанию:** `128` и `1024`

**Почему увеличиваем:**
- При большом количестве одновременных соединений (100+ клиентов)
- Без этого — новые соединения отклоняются
- 65535 — максимально допустимое значение

**Проверка:**
```bash
netstat -s | grep -i "listen\|syn"  # Сколько соединений в очереди
```

---

### net.ipv4.tcp_fin_timeout

**Что это:** Время ожидания FIN пакета перед закрытием сокета.

**Значение:** `30` секунд

**По умолчанию:** `60` секунд

**Почему сокращаем:**
- Быстрее освобождаем ресурсы
- Меньше TIME_WAIT сокетов

## Disk I/O & Virtual Memory

### vm.dirty_ratio

**Что это:** Процент памяти, заполненный "грязными" данными (которые ещё не записаны на диск).

**Значение:** `30%`

**По умолчанию:** `20%`

**Как работает:**
```
Чем больше dirty ratio:
- Больше буферизации в памяти
- Реже обращаемся к диску
- Лучше для последовательных операций (кино файлы)
- Но рискуем потерять данные при краше

Рекомендация для кино:
- 30% — хороший компромисс
- Не больше 40% (риск потерь)
```

**Команда проверки:**
```bash
cat /proc/meminfo | grep Dirty
sysctl vm.dirty_ratio
```

---

### vm.dirty_background_ratio

**Что это:** Процент памяти, при котором ФОНОВЫЙ процесс начинает писать на диск.

**Значение:** `10%`

**По умолчанию:** `5%`

**Различие:**
```
- dirty_background_ratio = 10%: фоновая запись начинается рано
- dirty_ratio = 30%: если достигаем 30% — приложение блокируется

Это создаёт окно 10-30% для оптимального буферизирования.
```

---

### vm.dirty_expire_centisecs

**Что это:** Время жизни "грязных" страниц перед принудительной записью на диск.

**Значение:** `3000` сантисекунд = 30 секунд

**По умолчанию:** `3000` (обычно не менять)

**Что происходит:**
```
Если данные в памяти 30+ сек и не записаны:
- Ядро принудительно пишет их на диск
- Гарантирует что данные не потеряются
```

---

### vm.dirty_writeback_centisecs

**Что это:** Интервал, с которым фоновый процесс пробегает и пишет грязные страницы.

**Значение:** `500` сантисекунд = 5 секунд

**По умолчанию:** `500` (обычно не менять)

**Оптимизация:**
```
Более частые проверки (5 сек) = больше маленьких записей
Но: более предсказуемое поведение системы
```

---

### vm.swappiness

**Что это:** Склонность ядра использовать SWAP (виртуальная память на диске).

**Значение:** `10`

**По умолчанию:** `60`

**Диапазон:** 0-100

**Почему уменьшаем на 10:**
```
Swappiness = 60 (по умолчанию):
- Система охотно использует SWAP
- Диск очень медленнее чем память
- Замораживает систему при обращении к SWAP

Swappiness = 10 (наша установка):
- Использует SWAP только при критической нехватке памяти
- Предпочитает выделить память приложению
- Лучше для высоконагруженных систем с достаточной памятью

Swappiness = 0:
- Вообще не использует SWAP
- Рискуем OOM (Out of Memory) если памяти недостаточно
```

**Мониторинг:**
```bash
free -h  # Смотрим Used в Swap
cat /proc/pressure/memory  # PSI метрики (если доступно)
```

## File System

### fs.file-max

**Что это:** Максимальное количество открытых файлов на всю систему.

**Значение:** `2097152` (2 миллиона)

**По умолчанию:** ~100K-200K (зависит от системы)

**Почему увеличиваем:**
- Каждое соединение = открытый файловый дескриптор
- При 100+ одновременных скачиваниях — быстро упираемся в лимит
- RAID диски могут требовать много дескрипторов

**Команда проверки:**
```bash
cat /proc/sys/fs/file-max
lsof -a | wc -l  # Сколько файлов открыто сейчас
```

---

### fs.inotify.max_user_watches

**Что это:** Максимум файлов, которые можно мониторить через inotify.

**Значение:** `524288` (512K)

**По умолчанию:** `8192`

**Почему увеличиваем:**
- Docker, systemd, приложения используют inotify
- При большом количестве файлов — не хватает

## Kernel Scheduling

### kernel.sched_preempt

**Что это:** Режим вытесняющего планирования процессов.

**Значение:** `1` (Full preemption)

**Варианты:**
- `0` — Voluntary preemption (процесс отдаёт управление сам)
- `1` — Full preemption (ядро может прервать в любой момент)

**Для кино:** Full preemption лучше для интерактивности и честного распределения.

## RAID Parameters

### dev.raid.speed_limit_min и dev.raid.speed_limit_max

**Что это:** Минимальная и максимальная скорость ресинка RAID массива.

**Значение:** `100000` и `200000` (KB/sec)

**Почему ограничиваем:**
```
Без ограничений:
- RAID может использовать ВСЮ пропускную способность диска
- Система замирает пока идёт ресинк
- Клиенты видят критический лаг

С ограничением:
- Ресинк идёт фоном
- Оставляем пропускную способность для приложений
- Система остаётся отзывчивой
```

**Расчёт:**
```
Для быстрого ресинка:
  speed_limit_max = (bandwidth / 4)
  
Пример: диск 200 MB/s → max 50 MB/s = 51200 KB/s

Для стабильности:
  speed_limit_max = (bandwidth / 10)
```

## Применение параметров

### Способ 1: Постоянно через /etc/sysctl.d/

```bash
# Копируем конфиг
sudo cp configs/99-performance.conf /etc/sysctl.d/

# Применяем
sudo sysctl -p /etc/sysctl.d/99-performance.conf

# Проверяем
sysctl -a | grep net.core.rmem_max
```

### Способ 2: Временно (до перезагрузки)

```bash
sudo sysctl -w net.core.rmem_max=134217728
```

### Способ 3: Через systemd service

```bash
sudo systemctl restart sysctl
```

## Мониторинг и проверка

### Проверить все оптимизации сразу

```bash
#!/bin/bash

echo "=== TCP Buffers ==="
sysctl net.core.rmem_max net.core.wmem_max

echo -e "\n=== Congestion Control ==="
sysctl net.ipv4.tcp_congestion_control

echo -e "\n=== Memory ==="
sysctl vm.dirty_ratio vm.swappiness

echo -e "\n=== File Descriptors ==="
sysctl fs.file-max
ulimit -n

echo -e "\n=== Network ==="
netstat -i | grep -v lo

echo -e "\n=== Disk I/O ==="
iostat -x 1 2 | tail -10
```

### Во время высоконагруженной операции

```bash
# Terminal 1: Мониторим I/O
watch -n 1 'iostat -x | grep -E "avg|sda"'

# Terminal 2: Мониторим сеть
watch -n 1 'netstat -i'

# Terminal 3: Мониторим память
watch -n 1 'free -h; echo; cat /proc/meminfo | grep Dirty'

# Terminal 4: Запускаем операцию (копирование кино)
cp /source/movie-50gb.raw /dest/
```

### Ошибки при применении

**Ошибка: "unknown key"**
```
Ядро не поддерживает этот параметр.
Это нормально — просто не применяется.
```

**Ошибка: "Permission denied"**
```
Нужны права root:
  sudo sysctl -p /etc/sysctl.d/99-performance.conf
```

**Параметр не применился**
```
Проверить:
  sysctl net.core.rmem_max
  
Если не совпадает с конфигом:
  1. Убедитесь что используется правильный файл конфига
  2. Проверьте что нет других конфигов, которые перезаписывают значение
  3. Может понадобиться перезагрузка
```

## Рекомендации по величинам для разных случаев

### Для локальной сети (1 Gbps, LAN)

```
Меньше буферизации нужно:
net.ipv4.tcp_rmem = 4096 87380 16777216    # 16MB вместо 64MB
net.ipv4.tcp_wmem = 4096 65536 16777216
```

### Для WAN / Интернета (высокий RTT)

```
Больше буферизации:
net.ipv4.tcp_rmem = 4096 87380 134217728   # 128MB (как у нас)
net.ipv4.tcp_wmem = 4096 65536 134217728
```

### Для очень мощных серверов (много памяти)

```
Можно ещё больше:
net.core.rmem_max = 268435456              # 256MB
net.core.wmem_max = 268435456
net.ipv4.tcp_rmem = 4096 87380 268435456
net.ipv4.tcp_wmem = 4096 65536 268435456

vm.dirty_ratio = 40                        # Больше буферизации
```
